# Репорт апстриму — конкурентность ядра на 2-м сообщении в сессии (2026.6.11)

Черновик для issue в openclaw core (или комментария к существующему
**#98562 «reply session initialization conflicted»**). Обнаружено при работе
VK-канала, но сбой — в **reply-dispatch / инициализации сессии ядра**, а не в
плагине канала.

> Русская копия для Ивана. Оригинал (для подачи апстриму — на английском):
> [core-concurrency-bug-report.md](core-concurrency-bug-report.md).

## Коротко

Когда второе входящее сообщение в **той же сессии** обрабатывается вскоре после
первого, ядро ломается одним из двух способов — в зависимости от того, *как*
второе сообщение попадает в диспетчер:

1. **Встало в очередь конкурентно (queueDepth ≥ 2) → deadlock.**
   `waitForReplyDispatcherIdle` у текущего ответа никогда не резолвится, пока в
   очереди есть сообщение, поэтому первый ответ виснет, и вся лань сессии стоит
   до срабатывания 15-минутного stuck-session abort.
2. **Задиспатчено сразу после завершения первого → `reply session
   initialization conflicted`.** Сессия остаётся «отравленной» несколько секунд
   после завершения сообщения; любая инициализация reply-сессии для этого ключа
   проваливает optimistic-commit в `auto-reply/reply/session.ts:936`, и ретраи
   **не** восстанавливают её.

В обоих случаях второе сообщение остаётся без ответа, а в случае (1) ещё и первый
ответ виснет вместе со всей ланью.

## Окружение

- openclaw **2026.6.11** (установка через pnpm), локальный gateway-демон (macOS).
- Канал: VK (`deliveryMode: "direct"` — тот же путь, что у discord/slack/matrix).
- Бэкенд: `claude-cli` (локально), один агент `main`, ключ сессии
  `agent:main:vk:direct:<peer>`.
- Воспроизводится на обычных текстовых сообщениях; media/TTS не нужны.

## Воспроизведение

1. Отправь сообщение **A** агенту в одном диалоге.
2. Пока A ещё обрабатывается (до доставки ответа), отправь сообщение **B** в
   **том же** диалоге.

Результат зависит от тайминга доставки (наблюдались оба):

- **B встаёт в очередь, пока A диспатчится** → ответ на A виснет ~15 мин
  (deadlock), восстанавливается только stuck-session abort'ом.
- **B диспатчится сразу после завершения A** → B немедленно падает с
  `reply session initialization conflicted for agent:main:vk:direct:<peer>`.

## Доказательства

### Случай 1 — deadlock (2-е сообщение в очереди)

```
message processed: ... messageId=3513 ... duration=979363ms reason=reply_operation_abort
```

Один ответ занял **979363 мс (~16 мин)** — он не работал столько на самом деле,
а висел в `waitForReplyDispatcherIdle` до `reply_operation_abort` (stuck-session
abort, `diagnostics.stuckSessionAbortMs`, дефолт 900000 мс). Всё это время лань
не обрабатывала ничего.

### Случай 2 — конфликт инициализации сессии (2-е сразу после 1-го)

Первое сообщение завершается штатно, затем второе падает за ~30 мс, ещё до
создания турна — и продолжает падать на каждом ретрае в течение 6+ секунд:

```
16:28:30.674 message dispatch completed: messageId=3527 outcome=completed duration=30431ms   ← msg A ок
16:28:30.689 session state: prev=processing new=idle reason="message_completed" queueDepth=0
16:28:30.986 message received:  messageId=3528                                                ← msg B
16:28:31.010 message dispatch started: messageId=3528
16:28:31.040 session state: prev=processing new=idle reason="message_error" queueDepth=0      ← 30 мс, без турна
16:28:32.9xx (ретрай) → message_error
16:28:34.8xx (ретрай) → message_error
16:28:36.7xx (ретрай) → message_error
... vk: message handler error: reply session initialization conflicted for agent:main:vk:direct:12324712
```

Ошибка бросается здесь:

```ts
// src/auto-reply/reply/session.ts:936
if (!committed.ok) {
  if (!staleSnapshotRetried) {
    return await initSessionStateAttemptLocked(params, attemptContext, true); // ядро ретраит один раз
  }
  throw new Error(`reply session initialization conflicted for ${sessionKey}`);
}
```

То есть optimistic-commit инициализации reply-сессии проваливается, ядро один раз
ретраит внутри, снова провал → бросает исключение. Важно: это держится
**несколько секунд после завершения первого сообщения** — это не
субмиллисекундная гонка.

## Что мы пробовали (со стороны канала) и что это говорит

Мы держим форк VK-плагина, поэтому смогли поэкспериментировать с путём доставки:

1. **Сериализация inbound по peer** — цепочка обработчиков, чтобы ядро никогда не
   видело `queueDepth ≥ 2` для диалога. ✅ **Убирает deadlock (случай 1).** Первое
   сообщение всегда завершается, лань живая. Это прямо указывает, что deadlock —
   именно в *очередном* пути `waitForReplyDispatcherIdle`.
2. **Settle-задержка (~750–960 мс) перед диспатчем 2-го сообщения** — ❌ конфликт
   (случай 2) не обходит.
3. **Ретрай всего inbound-обработчика на конфликте**, 3× с backoff 1.5 с — ❌ все
   4 попытки (первая + 3 ретрая) падают за ~6 с. Каждая проваленная попытка,
   похоже, снова трогает session-row и заново провоцирует конфликт.

Вывод: **случай 2 не восстановим извне ядра.** Сессия остаётся в состоянии, где
свежая инициализация reply-сессии не может закоммититься ещё несколько секунд
после завершения предыдущего сообщения.

## Предполагаемая причина / вопросы к мейнтейнерам

- Случай 1: `waitForReplyDispatcherIdle` (в `auto-reply/reply/dispatch-from-config.ts`)
  ждёт idle, но сообщение в очереди держит состояние non-idle → self-deadlock.
  Не должно ли очередное сообщение той же сессии вставать в очередь ЗА активным
  ответом, а не блокировать его?
- Случай 2: что пишет в session-row между чтением снапшота и коммитом в
  `initSessionStateAttemptLocked`, и почему оно продолжает писать спустя секунды
  после `message_completed`? Пост-completion асинхронный писатель (session meta /
  архивация / memory flush?), переживающий `reply_operation`, объяснил бы
  устойчивый stale-snapshot конфликт. Должна ли инициализация ждать этого
  писателя, или коммит должен быть идемпотентным / last-writer-wins для
  завершённой сессии?

## Влияние

- Любой пользователь, отправивший два быстрых сообщения в одном диалоге, ловит это.
- Случай 1 — худший: один зависший ответ замораживает всю лань на 15 минут.
- Случай 2 — быстрый видимый сбой (канал показывает ошибку), но второе сообщение
  молча теряется, пока пользователь не перешлёт его после паузы.

## Наш обход (со стороны канала, временный)

Мы сериализуем inbound по peer в VK-плагине (чинит случай 1). Мы намеренно **не**
пытаемся замазать случай 2 — ему нужен фикс в ядре. См. `src/monitor.ts`
(`inboundChainByPeer`, `VK_SERIALIZE_INBOUND`).
